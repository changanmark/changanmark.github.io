## 5.1 最简单动画

[源码：ch05_01_simple-animation.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch05/ch05_01_simple-animation.html)

球沿 Z 轴、锥沿 X 轴往返运动。`animate` 先给位置加固定增量，越过边界便把增量取反，再调用 `draw`。这能产生动画，却把运动速度绑在“更新次数”上。

### 源码时序

`render` 记录 `initialTime` 并启动 timer；`onFrame` 计算经过毫秒数，达到 `frequency=5` 才更新。若落后多个周期，`steps=floor(elapsed/frequency)` 后补做多次 `animate`。每次更新球加 0.1、锥加 0.15。

注意 `setInterval(onFrame, frequency / 1000)` 是明确的单位错误：setInterval 的参数本来就是毫秒，5/1000 会变成 0.005ms，浏览器最终按最小 timer 粒度频繁唤醒，再由 onFrame 自己拒绝大多数调用。正确至少应传 `frequency`，但屏幕动画更应使用 requestAnimationFrame。

### 每对象矩阵隔离

draw 先算基础 View/MV；遇到球时复制或 push 矩阵，平移 spherePosition，上传后恢复；锥同理。若不恢复，锥会继承球的 Z 平移。矩阵栈的 push 必须复制 Float32Array，而不是保存同一个引用。

### 边界反弹的细节

当前逻辑先移动后判断，越界时只反转速度，没有把位置拉回边界。因此对象可能在范围外停留一步，大步长时甚至穿越很远。最小修复是 clamp；更精确做法是算本步碰撞时刻，反射速度，再积分剩余时间。

### 正确的实时版本

```js
let previous;
function frame(now) {
  if (previous === undefined) previous = now;
  const dt = Math.min((now - previous) / 1000, 0.1);
  previous = now;
  spherePosition += sphereVelocity * dt;
  updateBounce();
  draw();
  requestAnimationFrame(frame);
}
requestAnimationFrame(frame);
```

velocity 的单位变成“世界单位/秒”，dt 是秒。限制 dt 可防止标签页暂停后恢复时一步穿墙。RAF timestamp 与 performance timeline 同源，不要和 Date.now 的 Unix 时间混算。

### 验收

在 60Hz 与 144Hz 屏幕分别运行 10 秒，记录位移；正确实现应近似一致。DevTools 模拟 CPU slowdown，动画可以不流畅，但相同真实时间后的状态不应明显变慢。

## 5.2 丢帧与固定模拟步

[源码：ch05_02_dropping-frames.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch05/ch05_02_dropping-frames.html)

此例把 `animationRate=300ms` 与 `simulationRate=30ms` 分开：约每 300ms 才进入一次更新，却按落后的模拟步数连续执行 animate，故意演示“显示帧少，不代表模拟时间也应变慢”。

### 代码审计

`steps=floor(elapsedTime/simulationRate)` 是 catch-up 思路，但循环中的每次 `animate` 仍使用固定位置增量，隐含“一个 step 就是 30ms”。更新后把 initialTime 直接设为当前时刻，会丢掉除不尽的余数；长期会产生漂移。更正确是 accumulator 保留余量。

同样，`setInterval(onFrame, animationRate / 1000)` 把毫秒误除 1000。它不会获得 300Hz 的精确 timer，只会造成无意义轮询；浏览器后台还会主动 throttle timer。

### 固定步长框架

```js
const fixedDt = 1 / 60;
let accumulator = 0, previous;
function frame(now) {
  if (previous === undefined) previous = now;
  accumulator += Math.min((now - previous) / 1000, 0.25);
  previous = now;
  let steps = 0;
  while (accumulator >= fixedDt && steps < 8) {
    previousState = clone(state);
    simulate(state, fixedDt);
    accumulator -= fixedDt;
    steps++;
  }
  render(interpolate(previousState, state, accumulator / fixedDt));
  requestAnimationFrame(frame);
}
```

固定 dt 让碰撞、积分和可重放结果稳定；插值 alpha 只用于显示，不反过来改变模拟状态。最大步数避免机器追不上时陷入“越补算越落后”的死亡螺旋。

### 光源分支

`uUpdateLight` 控制光位置是否随 MV 转换。无论 fixedLight 名字怎么写，顶点、法线、光线向量最终必须位于同一坐标空间；否则动画相机移动时光照会出现非物理跳动。

### 验收

故意每秒阻塞主线程 200ms，记录模拟时间、真实时间和绘制帧数。恢复后可见画面会跳过中间帧，但球的位置应追上真实时间。再去掉 accumulator 的余数保留，运行数分钟并测量累计漂移。

## 5.3 50 个弹跳球

[源码：ch05_03_bouncing-balls.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch05/ch05_03_bouncing-balls.html)

本例为每个球建立 `BouncingBall` 状态对象：三维位置、起始高度 H0、初速度 V0、落地速度 VF、反弹起始时间、弹性系数和颜色。几何仍被加载 50 次，因此它同时是下一节的性能基线。

### 运动方程

`h(t)=H0+V0·t−½g·t²` 是恒定重力下的位置解析解。第一次从静止高度 H0 落下，落地速率由能量关系 `VF=sqrt(2gH0)` 得到。碰地后，源码令新上抛速度 `V0=VF·BOUNCINESS`，最大高度 `HF=V0²/(2g)`。

弹性系数理应通常在 0～1；源码 `(Math.random()+0.5)` 会产生 0.5～1.5，超过 1 的球每次反弹会获得能量并越跳越高。这不是数值误差，而是参数定义允许“主动球”。若要耗散，限制到 `<1` 并设置低速休眠阈值。

### 碰撞离散误差

当 h≤0 时源码重置 bouncingTime，却没有把 `position[1]` 明确写为 0，也没有处理本步穿过地面的剩余时间。因而会悬留上一高度一帧或产生相位误差。可靠做法可解二次方程求碰地时刻，先积分到碰撞、反射速度，再积分余下 dt；简单版至少 clamp 高度为 0。

### 时间实现中的问题

`sceneTime += 33/1000` 把每次 animate 固定解释为 33ms；而 timer 的目标 simulation interval 是 15ms，二者不一致。于是物理时间跑速由回调次数决定。应让 update 接收统一 fixedDt 或真实 timestamp，不能同时维护互相矛盾的时钟。

### 绘制成本

场景为每个球加载同一 JSON 并建立对象。每帧 traverse 时解析 alias 得球索引，逐球计算矩阵、上传 uniform、绑定 VAO/EBO、draw、解绑。50 次 draw 不一定慢，但重复资源、字符串解析和状态切换都是可测的 CPU 成本。

`gl.clearDepth(100)` 会 clamp 到合法 [0,1]，等效于 1，并不能扩大 far plane。VAO 已保存 EBO 绑定时，绑定 VAO 后通常无需再次 bind ELEMENT_ARRAY_BUFFER。

### 验收

把重力设为 9.8、H0=19.6，理论首次落地约 2 秒；记录实际 sceneTime。令 bounciness=0.5，反弹高度理论为原高度的 0.25。使用单球验证后再扩展到 50 球；否则群体画面会掩盖物理错误。

## 5.4 500 个弹跳球：优化版

[源码：ch05_04_bouncing-balls-optimized.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch05/ch05_04_bouncing-balls-optimized.html)

优化版把球数从 50 提到 500，却只加载一次 `ball` 几何。所有实例共享 VAO、VBO、IBO；每个球只保存 position/color/physics state。

### 优化发生在哪里

`drawBalls` 先设置球共有的 ambient/specular/wireframe，打开 `uTranslate`，并只绑定一次 sphere VAO。循环中 `drawBall` 只上传 `uTranslation`、diffuse color，然后 drawElements。相较上一节，它消除了 499 份 GPU 几何、重复矩阵栈操作及大量 bind/unbind。

顶点 shader 在 `uTranslate` 为真时对顶点加平移。这只适用于纯平移；实例还需旋转/缩放时可传 mat4 的四列，或传 translation/quaternion/scale 后在 shader 构造。

### 尚未消除的成本

500 个球仍有 500 次 uniform 更新和 500 次 draw call。CPU 到驱动的命令提交可能成为瓶颈。WebGL2 原生实例化可把每球 position/color 放入 instance buffer：

```js
gl.vertexAttribDivisor(positionLoc, 1);
gl.vertexAttribDivisor(colorLoc, 1);
gl.drawElementsInstanced(gl.TRIANGLES, indexCount,
                         gl.UNSIGNED_SHORT, 0, ballCount);
```

divisor=1 表示 attribute 每个实例推进一次，而非每顶点推进。动态数据每帧用 `bufferSubData` 更新；不要每帧 createBuffer。大量对象还可把物理更新放入 typed arrays，改善内存局部性并减少 GC。

### 性能测量

优化不能只看 FPS。记录 CPU frame time、draw call 数、buffer/texture 数和显存估计；用浏览器 Performance 判断时间在 JS 循环、uniform 调用还是 GPU。若 fill rate 才是瓶颈，减少 draw calls 未必提升。

### 原物理问题仍存在

共享几何不会自动修复 0.5～1.5 弹性系数、离散碰撞和固定 sceneTime 的问题。性能重构应以相同输入得到相同状态；先写单球测试，再比较 50/500 版本在相同时间点的位置。

### 验收

在两版中固定随机种子和球数，比较每帧 draw calls、VAO binds 和 GPU buffer 数。再实现实例化，使球的 draw call 从 N 降为 1；改变一个 instance color，确认只影响对应球。

## 5.5 线性插值

[源码：ch05_05_interpolation.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch05/ch05_05_interpolation.html)

球从 `P0=[-25,0,20]` 移到 `P1=[40,0,-20]`。源码预先生成 1000 个位置，动画只用 `position[sceneTime]` 查表。

### 数学与源码对应

线性插值为 `P(s)=(1−s)P0+sP1=P0+s(P1−P0)`。源码先计算每轴差值除以 incrementSteps，再循环 push；这与上式等价。s=0 得 P0，s=1 得 P1，0<s<1 位于线段内。

循环只生成 i=0…999，因此若步长按 `/1000`，最后样本是 s=0.999，并不精确包含终点；sceneTime 到 1000 又直接回 0。若必须命中两端，可生成 N+1 个样本，或用 `s=i/(N-1)` 生成 N 个。

### 参数速度与真实速度

直线且 s 随时间匀速时，空间速度恒定；但代码每 render tick 增一个索引，速度仍依赖 tick 频率。正确是由 elapsed/duration 算 `s=clamp(elapsed/duration,0,1)`，直接求位置，无需存 1000 个数组。

easing 是对时间参数变换：`s'=ease(s)`，再求 `lerp(P0,P1,s')`。例如 smoothstep `s²(3−2s)` 让起止速度为 0，但路径仍是同一条直线。

### 浮点与外推

clamp s 到 [0,1] 是限制在线段；允许 s<0 或 >1 就是线性外推。不要用浮点相等判断动画结束，使用 `s>=1`。若要循环，可对 elapsed 做 modulo；往返用三角波参数。

### 验收

手算 s=0、0.25、0.5、1 的位置并与程序输出比对。把 incrementSteps 改成 4，逐帧观察是否命中终点。最后改为 duration=2 秒，验证不同刷新率下都恰好约 2 秒到达。

## 5.6 Lagrange 与 B-Spline

[源码：ch05_06_interpolation-final.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch05/ch05_06_interpolation-final.html)

最终例提供五个控制点和三种插值：首尾直线、穿过全部控制点的 Lagrange 多项式、三次 clamped B-Spline。GUI 选择算法后 `resetAnimation` 清空位置并重新预采样。

### 线性模式

`doLinearInterpolation` 只读取第一个与最后一个控制点，中间三个对路径没有贡献。这是刻意的对照。循环中 `s=i/incrementSteps` 同样不含精确 s=1。

### Lagrange 模式逐式理解

N 个控制点分配参数节点 `x_i=i·dT`。第 i 个基多项式：

```text
L_i(x) = ∏(x-x_j)/(x_i-x_j), j≠i
P(x)   = Σ P_i L_i(x)
```

在 x=x_i 时，L_i=1、其余基为 0，因此曲线穿过每个控制点。源码先把分母存入 D，`Lk(x,axis)` 对 x/y/z 各算一次加权和。修改一个点会影响整条曲线；高阶且节点均匀时可能出现 Runge 振荡，因此它不是通用动画路径的首选。

### 三次 B-Spline

源码令次数 P=3，构造两端重复四次的 clamped knot vector U。零次基 `N_i,0` 判断 u 位于哪个 knot interval；`Np` 用 Cox–de Boor 递归：

```text
N_i,p(u) = (u-U_i)/(U_{i+p}-U_i) N_i,p-1(u)
         + (U_{i+p+1}-u)/(U_{i+p+1}-U_{i+1}) N_i+1,p-1(u)
```

分母为 0 时该项系数取 0，避免重复 knot 除零。曲线 `C(t)=ΣP_i N_i,3(t)`。局部支撑意味着移动一个控制点只改变附近若干 knot span；通常不穿过中间点，但 clamped 两端会命中首尾。

源码额外 push `C(1.0)` 是因为零次基使用半开区间 `[U_i,U_i+1)`，端点需要特殊照顾。实际仍应测试 C(1) 是否由递归实现正确返回末点；健壮实现常对 u==最后 knot 作显式处理。

### 采样不等于匀速

三种函数都把参数等分后存入 position。曲线在相同 Δt 上走过的空间距离可能不同，所以球会忽快忽慢。若需要空间匀速：密采样曲线，累加弦长得到 `s(t)` 表，按目标距离二分反查 t；更高精度可数值积分 `|C'(t)|`。

### 朝向与连续性

位置导数是切线，可把模型前轴对齐 normalize(C')。分段线性连接点只有 C0 连续；B-Spline 在普通 knot 处通常有更高连续性。三维路径不要盲用 Frenet frame：曲率接近 0 时法线不稳定，parallel-transport frame 更少翻转。

### 复杂度与改写

当前递归基函数在每个样本/控制点/坐标上重复计算，适合教学但浪费计算。可缓存 basis，或用 de Boor 算法直接求点。动画阶段也可实时求值，避免 position 大数组；路径不变且反复播放时预采样则很合理。

### 验收

检查 Lagrange 是否逐一穿过五点，B-Spline 是否只命中首尾。拖动中间点，比较两者影响范围。显示相邻样本距离曲线，验证等参数采样不是匀速；加入弧长重参数化后，距离曲线应明显变平。
