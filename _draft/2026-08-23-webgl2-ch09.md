## 9.1 应用骨架与生命周期

[源码：ch09_01_scaffolding.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch09/ch09_01_scaffolding.html)

本例只有 configure、draw、init：取得 canvas/context，设置 clear/depth/blend function，创建空 Program/Scene/Clock，再在 tick 调空 draw。它要建立的是顺序，而非视觉效果。

推荐生命周期：DOM ready → context/default state → 编译 program → camera/scene/render resources → await 必需资产 → controls → RAF update/render → dispose。资源未 ready 就启动 draw 会让错误随机依赖网络速度。

源码调用 `blendFunc` 却没有 `enable(BLEND)`，所以当前混合因子不生效。这很好地说明 WebGL 是状态机：参数状态与功能开关互相独立。每个 render pass 应完整声明 framebuffer、viewport、program、depth test/write/function、blend、cull 和纹理，而不是依赖 configure 中某次设置。

Clock 封装 RAF 时仍应把 timestamp/dt 传给 update。draw 不应创建 program/buffer/texture；这些是生命周期资源。SPA 卸载、热重载或换场景时要 cancel RAF、解绑事件并 `deleteProgram/deleteBuffer/deleteTexture/deleteVertexArray`。

上下文还可能触发 webglcontextlost/restored；lost 时 preventDefault 并暂停，restored 后所有 GPU resource 都需重建，JS 对象仍在不代表显存对象有效。

验收：给 configure/draw/dispose 打有序日志；连续挂载/卸载页面 20 次，监听器与 RAF 数量不增长；故意让 shader compile 失败时不启动 render loop。

### 最小 Draw 契约

即使场景为空，draw 也应在 resize 后设 viewport，bind 默认 framebuffer，设 clear color/depth 并 clear；这样之后添加 Scene 不会继承 PostProcess/Picker 的目标。Clock tick 只请求一帧，绘制函数不自行递归启动第二套 RAF。

工程入口让 `async init()` 返回 app/dispose handle，任何阶段失败都清理已经创建的资源。用 AbortController 取消未完成 fetch，防页面卸载后回调重新把对象塞回 scene。

## 9.2 展厅、材质与资源所有权

[源码：ch09_02_showroom.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch09/ch09_02_showroom.html)

展厅载入 floor 与汽车多个 part。shader 支持 illum=0 无光照、1 diffuse、2 diffuse+specular；材质字段沿 OBJ/MTL 习惯为 Ka/Kd/Ks/Ns/d/illum，四盏灯提供 position/Ld/Ls。

### 从文件到 draw call

`loadCar` 清 scene.objects、重新加入 floor，再调用 `scene.loadByParts(path,partsCount)`。每个 part JSON 被请求、解析、补默认材质，创建 position/normal buffer、index buffer、VAO，最后进入 objects。调用 loadByParts 返回不等于全部请求完成；应返回 Promise 并 `await Promise.all` 后才设置 ready。

fetch 必须检查 `response.ok`；同 URL 应缓存 Promise 防止重复请求/上传。切车时直接 `scene.objects=[]` 只移除 JS 引用，若 Scene 没有 delete 旧 VAO/VBO/IBO 就泄漏 GPU 资源。需要 Mesh 引用计数或显式 dispose。

### 数据更新频率

相机 View/P 与灯是 per-frame；材质是 per-material；Model/MV/Normal 是 per-object。WebGL2 UBO 可把 frame block 和 material block 分开，避免每 part 重传四盏相同灯。当前 draw 每对象上传 Ka/Kd/Ks/Ns/d/illum，再 bind VAO/draw，是清晰基线。

### Shader 空间审计

顶点 vertex 在 eye space，lightPosition 却直接从 uniform 包成 vec4，意味着 uniform 必须已是 eye space；若数据实际是 world space且相机旋转，会空间不一致。`vEye=-vertex.xyz` 正确表示 eye 在观察原点。法线用 vec4 时 w 应为 0，源码写 1 会让某些矩阵平移污染方向。

### 材质与透明

`uD` 输出 alpha，但 configure 只设置 blendFunc，未 enable BLEND；即使开启，也需把透明 part 分队列、关闭 depth write 并后向前排序。`object.value || default` 会把合法 0 覆盖掉，默认值应使用 `??`。

### 渲染器边界

教学 Scene 同时做 fetch、解析、GPU 上传、对象列表与遍历。工程应拆 AssetManager、Mesh、Material、Renderable、Scene 与 Renderer；Program 拥有 shader program，但不拥有 Mesh buffers。这样切车、缓存和销毁才有明确责任。

验收：跟踪一个 car part 从 URL 到 VAO 的每一步和拥有者；模拟一个 part 404，页面应报告具体 URL 且不悄悄半成品运行；切车 20 次后 GPU resource 数不持续增加。

## 9.3 控制层与状态同步

[源码：ch09_03_showroom-controls.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch09/ch09_03_showroom-controls.html)

本例在展厅上加入相机拖动、回家、车漆、光源 diffuse/specular、背景和 floor 显隐。好的结构是输入层只修改 application state，下一帧 renderer 统一把状态提交 GPU。

源码部分 GUI callback 直接 `gl.uniform3fv`。这依赖“正确 program 此刻正是 current program”，也可能下一对象 draw 立即覆盖。若以后有 picking/postprocess 多 program，回调在另一 program 当前时会写错或产生 INVALID_OPERATION。应修改 lights/material 数据并设 dirty flag；frame begin/material bind 时上传。

`eachCarPanel` 通过 alias substring 找车漆零件，这是逻辑标签筛选。alias 不应作为 GPU resource ID；若多个 part 匹配，遍历修改是合理的，若只取第一个则要明确 find/get 语义。

UI 名为 Shininess 的 callback 实际把 `[v,v,v]` 写到 Ks（镜面颜色/强度），没有修改 Ns（高光指数）。这会让用户把“更亮”误当“更尖锐”。正确控制应分别暴露 Specular Strength/Ks 和 Shininess/Ns。

相机 controls 应使用 Pointer Events/pointer capture，拖动只改 azimuth/elevation/dolly。home position、focus 等数组要 copy，不能让保存的 home 与当前 position 共享可变引用。

渲染队列方面：visible=false 应在上传 object uniforms 前剔除；opaque 可按 program→material→mesh 排序减少状态切换并 front-to-back；transparent 先按 view depth；floor/axis/debug 独立 pass。源码 `LINES` 读取 triangle indices 并不是真正网格边线。

验收：打开状态日志，在不绘制的 GUI 时刻确认不再调用 GL；修改 Ks 和 Ns 分别观察高光强度/宽度。切换多 program 后所有 controls 仍只改变数据，不依赖 current program。

### 输入到像素的时序

pointer/GUI event 修改 camera/material/light state→标 dirty→下一 Clock tick 更新 View/P 与灯数组→构建队列→逐 part 绑定材质/VAO并 draw。所有变化在同一 frame boundary 生效，不会出现一半 part 用新灯、一半仍用旧灯。

车型切换是异步状态机：loading 时旧车保留或显示占位；新车全部 ready 后原子替换；失败则保留旧车并显示错误。直接清 `scene.objects=[]` 再发请求会造成空场闪烁和旧资源泄漏。

## 9.4 Delta-ray 面光源近似

[源码：ch09_04_showroom-delta-ray.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch09/ch09_04_showroom-delta-ray.html)

此例不是 ray tracing。它仍是普通光栅化：每个片元围绕每盏灯的 light ray 做 5×5 个方向扰动，累加 diffuse/specular，尝试模拟扩展光源的柔和贡献。

`lSize=2` 使 x,z 循环各从 -2 到 2，共 25 样本；`invTotal=1/25` 只乘 diffuse。specular 没乘 invTotal，理论会随样本数放大约 25 倍。增加采样数时亮度不守恒，是明确的归一化缺陷。

还有循环偏移错误：dx 在每个 x 迭代前 `dx+=step`，没有由 x 直接计算；dz 只在每盏灯开始清零，却没有在每个 x 行重置，因此不断累加。正确应是 `dx=float(x)*step; dz=float(z)*step`。当前样本不是以灯中心对称分布。

vEye 被声明为 `[numLights]`，但每个元素都写同一个 `-vertex.xyz`，浪费 varying；只需一个 vec3。`projectOnPlane`、LT 等未参与最终输出，会被优化。JS 还调用 `program.uNi/object.Ni`，shader 和 uniform 列表并未声明 uNi；向 undefined location 调 uniform 可能抛 TypeError，应删除或真正声明其用途。

更清晰的面光源近似应在 CPU/shader 构造 2D 面上的样本位置 `lightCenter + right*dx + up*dz`，逐样本算 L、距离衰减、N·L 和 specular，所有贡献除样本数。固定规则网格会有结构性噪声；实时软阴影还涉及可见性测试，本例没有求遮挡，因此只是扩大高光/漫反射方向分布。

四灯×25 样本意味着每片元约 100 次循环，像素成本显著。使用 GPU timer，减半分辨率与减半样本数分别测量；不要只看 FPS。

验收：先用一个灯和 1 样本对齐上一例；再以 3×3、5×5 增加样本，归一化后总亮度近似不变；把样本位置着色/可视化，确认围绕中心对称，最后再讨论柔和效果。

### GPU 与渲染状态

100 次 sample loop 发生在每个通过 rasterization 的片元，汽车越大、分辨率越高成本越高；VBO/draw call 数不变并不代表性能不变。源码 blendFunc 未配 enable BLEND 的老问题仍在，uD<1 不会自动透明。

现代改写把 area-light samples 做成确定的局部二维点集，灯提供 center/right/up/extent；必要时减少样本并使用 temporal jitter+累积。若要真实软阴影，每个样本还需 visibility，光栅管线通常用 shadow map/PCF，而非仅扰动 L。
