## 4.1 模型与相机平移

[源码：ch04_01_model-view-translation.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch04/ch04_01_model-view-translation.html)

### 本例真正要解决的问题

屏幕上物体向左移动，既可能是物体在世界中向左，也可能是相机向右。像素结果相似，语义却不同：模型变换只影响一个对象，观察变换影响整个世界。本例用 GUI 分开控制二者，是理解后续相机系统的最小实验。

### 五个坐标空间

模型文件中的顶点首先处于 local/model space。`M` 把它放到 world space；`V` 把整个世界转换到以相机为原点的 view/eye space；`P` 得到 clip space。GPU 随后做透视除法 `(x,y,z)/w` 得到 NDC，viewport 再把 `[-1,1]` 映射到像素。

列向量约定下完整式为：

```text
p_world = M p_local
p_eye   = V p_world
p_clip  = P p_eye
```

因此代码中合成 `MV` 时是 `V · M`，右边的 `M` 先作用。交换次序一般会得到不同结果。

### 为什么相机移动取反

相机的 world matrix `C` 描述“相机对象怎样放进世界”；渲染需要反向问“一个世界点在相机坐标中在哪里”，所以 `V=C⁻¹`。纯平移时，`C=T(cx,cy,cz)`，其逆就是 `T(-cx,-cy,-cz)`。

数值验证：局部原点经模型平移 `(+2,0,0)` 后为 `(2,0,0)`；相机位于 `(1,0,0)`，View 平移 `(-1,0,0)`，最终观察坐标为 `(1,0,0)`。这也解释了相机右移时画面整体左移。

### 沿源码执行

页面加载公共 `Program`、`Scene`、矩阵库和 GUI。`configure` 取得 WebGL2 上下文，设置 viewport、清屏色和深度测试，编译链接 shader，缓存 attribute/uniform location，再异步装载场景。资源完成后才允许 draw；否则 VAO 尚未建立。

每帧先清 color/depth buffer，再依据 GUI 的 model translation 与 camera translation 重建矩阵，上传 `uModelViewMatrix`、`uProjectionMatrix`、`uNormalMatrix`。随后逐对象绑定 VAO、写材质 uniform 并调用 `drawElements`。uniform 是当前 program 的持久状态；若某对象漏写材质，它会继承上一次 draw 的值。

### GPU 看到了什么

位置 attribute 每个顶点读取一次。一次 draw 中所有顶点共享同一个 MV/P。顶点 shader 输出 clip position；光栅化器只对裁剪后的三角形产生片元。`DEPTH_TEST` 开启后，较近片元通过并写入 depth buffer，使绘制顺序不再直接决定不透明表面的可见性。

### 法线不能直接当位置

位置使用齐次 `w=1`，方向使用 `w=0`，因此平移不应影响法线。对包含非均匀缩放的 MV，法线矩阵应为 `N=(MV⁻¹)ᵀ` 的左上 3×3。若直接用 MV，法线可能不再垂直于表面，Lambert 明暗会错。

### 易错点与现代写法

- gl-matrix 原地运算的参数是 `(out,a,v)`；必须确认输出矩阵是否会覆盖仍需使用的输入。
- Canvas CSS 大小不是 drawing buffer 大小。resize 后要同步 `canvas.width/height`、`gl.viewport` 和投影 aspect。
- 工程中最好保留 `modelMatrix`、`viewMatrix`，只在上传或批处理中合成 MV，调试坐标空间更清楚。
- 以 `mat4.fromTranslation` 重建矩阵比在旧矩阵上反复 translate 更不易积累状态。

### 验收实验

把模型 X 设为 +2、相机 X 设为 +1，确认净位移等价于 +1；然后同时给二者 +10，观察相对位置不变。再放两个对象，只平移其中一个的 M，确认另一对象不动；只平移 V，则二者一起移动。

## 4.2 模型与相机旋转

[源码：ch04_02_model-view-rotation.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch04/ch04_02_model-view-rotation.html)

平移的逆只是改符号，旋转的逆则是反向旋转；对正交旋转矩阵还有 `R⁻¹=Rᵀ`。本例让 GUI 同时改变模型和相机的 X/Y/Z 欧拉角，用视觉结果建立“相机转向与世界反向旋转”的直觉。

### 角度与组合顺序

界面通常显示度，gl-matrix 的 `rotateX/Y/Z` 接收弧度，所以必须乘 `Math.PI/180`。45 若被误当弧度，相当于约 2578°，最终只剩周期后的奇怪角度。

矩阵乘法不交换：`Ry · Rx · p` 表示先绕 X、再绕 Y；`Rx · Ry · p` 是另一条轨迹。源码依次调用 rotateX、rotateY、rotateZ 时，要结合库的后乘约定判断实际作用顺序，不能只按代码从上到下凭感觉阅读。

### 相机旋转为何看起来相反

相机姿态 `C` 绕 Y 转 +θ，View 使用 `C⁻¹`，等价于把世界绕 Y 转 −θ。模型旋转改变模型相对于世界的朝向；相机旋转改变观察坐标轴。二者即使画面一时相同，也会在加入其他物体和世界光源后显出区别。

### 旋转中心

直接 `R p` 总是绕局部原点旋转。若枢轴为 `q`，应使用：

```text
M = T(q) · R · T(-q)
```

先把枢轴移到原点，旋转，再移回。模型“公转”通常不是 WebGL 错，而是模型原点、枢轴或矩阵顺序错。

### 法线与旋转

纯旋转时法线可乘同一个 3×3 旋转矩阵，因为逆转置仍是它本身。但教程仍建立 normal matrix，这样以后加入缩放不用改 shader 接口。normal 变换后要 normalize；插值也会改变长度，所以片元 shader 中还应再次 normalize。

### 欧拉角的边界

欧拉角易于 UI 教学，但存在万向锁：两个旋转轴在某些姿态重合，丢失一个自由度。自由飞行相机宜用单位四元数累计增量旋转，并定期 normalize；最终再转成矩阵。轨道相机只需要受限 yaw/pitch，欧拉角仍很实用，同时要限制 pitch 避免翻转。

### 调试实验

只给模型 Y=90°，记录模型局部 +Z 最终指向；清零后只给相机 Y=90°，比较画面方向。再同时设置 X=30°、Y=45°，交换源码中的两次 rotate 调用，观察结果不是简单交换 UI 数值。最后把 rotation matrix 的三个轴画成 RGB 线段，可直接发现轴向和手性错误。

## 4.3 完整 Model–View 实验

[源码：ch04_03_model-view.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch04/ch04_03_model-view.html)

前两节分别隔离平移和旋转，本例把它们合并，并允许在 “Model Coordinates” 与 “Camera Coordinates” 两种解释间切换。核心不是新增 API，而是明确同一组位置/角度被写入哪一张矩阵。

### 初始化、更新、上传三阶段

`initTransforms` 创建 `cameraMatrix`、`modelViewMatrix`、`projectionMatrix`、`normalMatrix`。`updateTransforms` 从当前 GUI 状态重新构造；`setMatrixUniforms` 才把 CPU 的 Float32Array 复制到当前 program 的 uniform storage。把三阶段分开可避免“JS 矩阵已经变了，但 GPU 仍在用上一帧”的误判。

透视矩阵明确使用 `45 * Math.PI/180`，aspect 取 drawing buffer 宽高比，near/far 为 0.1/1000。near 必须大于 0；透视深度非线性，near 过小会把大量精度浪费在相机附近。

### 两种分支的语义

Model 分支从单位阵开始，依次加入位置和旋转，得到对象的 MV。Camera 分支先构造相机姿态 `C`，再 invert 得到 View。切换分支时画面可相似，但光源也必须与顶点、法线处于同一空间，否则相机旋转后高光会“粘在屏幕上”或漂移。

源码的 `setMatrixUniforms` 中存在值得逐行审计的矩阵复用：invert、transpose 的输入输出变量名容易让 `cameraMatrix`、`modelViewMatrix` 和 `normalMatrix` 的语义失真。现代改写建议显式写：

```js
mat4.invert(viewMatrix, cameraWorldMatrix);
mat4.multiply(modelViewMatrix, viewMatrix, modelMatrix);
mat3.normalFromMat4(normalMatrix, modelViewMatrix);
```

`mat3.normalFromMat4` 也让 shader 的 `uNormalMatrix` 改为 mat3，避免把方向包装成 vec4 时误写 `w=1`。

### draw 的状态顺序

每帧清屏后更新变换；每对象先设置材质和 wireframe 标志，再绑定 VAO，依据对象模式调用 draw。VAO 保存 attribute 格式及 ELEMENT_ARRAY_BUFFER 绑定，却不保存 program、uniform、blend/depth 开关。状态归属必须分清。

### 性能与正确性

教学代码每帧重算所有矩阵便于理解。工程中可给 camera/model 加 dirty flag：只有位置、姿态、FOV、viewport 改变时才重算。但不要过早缓存错误矩阵；先用已知点验证每个空间，再优化。

验收时选择局部点 `(0,0,0,1)`，手算 M、V 后的位置并与 shader 调试输出比较。再引入非均匀缩放 `(2,1,0.5)`，分别用 MV 和 inverse-transpose 变换法线，检查哪个仍与切线点积为 0。

## 4.4 Orbiting 与 Tracking 相机

[源码：ch04_04_camera-types.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch04/ch04_04_camera-types.html)

这一节开始使用公共 `Camera.js`。Camera 保存的是相机在世界中的姿态/位置，而 shader 需要 View；`getViewTransform()` 因此返回相机矩阵的逆。

### 两种交互模型

Orbiting（轨道）以目标为中心，用方位角 azimuth、仰角 elevation 和距离 distance 表示相机。旋转时 eye 沿球面移动并始终看向目标，适合模型查看器。Tracking（跟踪/自由观察）更像移动摄像机：改变相机自身位置和朝向，目标不会自动保持在画面中心。

同样的 translate/rotate 调用，因为相乘顺序不同会产生“绕目标公转”或“原地转头”。阅读 Camera 时要把矩阵调用改写为变换式，而不是只看函数名。

### 相机局部轴

Camera 从矩阵导出 right、up、normal 三个方向。方向使用齐次 `w=0`，否则矩阵的平移列会污染方向。三个轴应保持单位长度且两两垂直；连续浮点运算后可用 normalize/Gram–Schmidt 或四元数重建。

`dolly` 沿相机 normal 前后移动，这是改变相机位置；改变 FOV 是 optical zoom。前者会改变视差和相机与物体距离，后者不改变视点，只改变视锥开角。两者不应共用一个含糊的 zoom 变量。

### 鼠标到角度

controls 将像素位移 dx/dy 转成角度增量。应按 canvas 尺寸或设备无关灵敏度缩放，并使用 Pointer Events：pointerdown 后 `setPointerCapture`，pointermove 更新，pointerup 结束。否则指针离开 canvas 会丢失拖动状态。现代键盘处理用 `event.code`，不使用已废弃的 keyCode。

### 极点与 lookAt 退化

lookAt 常由 `z=normalize(eye-target)`、`x=normalize(cross(up,z))`、`y=cross(z,x)` 构造。当视线平行 up 时叉积接近零，矩阵退化。轨道相机通常把 elevation 限在略小于 ±90°；或者在接近极点时选择备用 up。

### 验收

Orbiting 模式拖动时检查目标是否始终位于中心，dolly 时观察透视是否改变；Tracking 模式原地 yaw 后，确认相机 position 未绕目标变化。打印 `dot(right,up)` 等三个点积应接近 0，三个轴长度应接近 1。

## 4.5 汽车模型、相机与固定光源

[源码：ch04_05_car.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch04/ch04_05_car.html)

汽车由多个网格/零件组成，但共享一台 Camera、一个 Projection 和同一套光照 program。本例把前面的小对象实验放大到真实尺度，暴露裁剪面、光源空间和状态复用问题。

### 共享与逐对象状态

一帧内 View/P 通常只需上传一次；每个零件改变 model/material 后绘制。仓库场景数据若已经把零件顶点放在共同坐标系，M 可以相同；若各零件保留局部坐标，必须为每个对象计算 `V·M_i`。不要因为变量名都叫 modelView 就假设其内容一致。

### 固定光源的两种含义

“固定”可能指固定在世界，也可能固定在相机。

- 世界灯：位置先由 world 定义，每帧乘 V 进入 eye space。转动相机后灯照射在车身上的世界位置不变。
- 相机灯：直接在 eye space 定义，例如 `(0,0,5000)`；相机旋转时它随镜头走，类似头灯。

源码 `uFixedLight` 在 shader 中选择是否用 MV 变换光源，是教学对照。严格实现应只用 View 变换世界灯，不能乘对象 M，否则不同对象会“看到”不同灯位。

### 深度精度

本例 far=5000、near=0.1，比值为 50000。透视深度精度集中在 near 附近；过小 near 会增加远处 z-fighting。先计算汽车包围盒与相机最近距离，再把 near 尽量推远、far 尽量拉近。`clearDepth(1)` 才是默认深度范围远端；传 100 也会被 clamp 到 1，并不会扩大可见距离。

### 法线矩阵审计

源码通过 camera matrix 的 transpose 构造 normal matrix 的写法只在特定纯旋转/变量语义下成立。稳妥公式仍是每个对象 `inverseTranspose(V·M)`。若汽车零件有非均匀缩放，错误立即表现为光照角度异常。

### 验收实验

切换两种 camera，再开关 Static Light Position：分别判断高光属于世界还是屏幕。把 near 从 0.1 增到 10，观察远处共面闪烁是否减轻，同时确认最近几何是否被裁掉。最后逐零件显示其包围盒，验证 home position 与 far 是依据数据而非猜测选择。

## 4.6 透视投影与正交投影

[源码：ch04_06_projection-modes.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch04/ch04_06_projection-modes.html)

Model/View 决定相机眼中顶点的位置，Projection 决定如何把观察空间视体映射到裁剪空间。本例允许在 perspective 与 orthographic 间切换。

### 透视投影

`mat4.perspective(out,fovy,aspect,near,far)` 的 fovy 是纵向视场角且单位为弧度。投影后 GPU 在齐次坐标中裁剪 `-w≤x,y,z≤w`，再做透视除法。观察空间中更远的点产生更大的 `w`，所以除法后更靠近中心，形成近大远小。

FOV 越大像广角，物体显得小且透视夸张；FOV 越小像长焦，物体显得大且透视压缩。改变 FOV 不等于 dolly：它不改变视点和视差。

### 正交投影

`mat4.ortho(out,left,right,bottom,top,near,far)` 把长方体线性映射到裁剪体，没有按距离缩小。适合 CAD、UI、阴影贴图。保持比例时可令半高为 h、半宽为 `h*aspect`。示例若复用名为 fov 的 GUI 值来控制正交范围，只是 UI 复用，它已不再是角度。

### 裁剪、NDC 与 viewport

三步不要混淆：Projection 产生 clip coordinates；透视除法产生 NDC；viewport 只把 NDC 映射到 framebuffer 像素。viewport 改宽高不会修复错误 aspect，只会把已经错误的图拉伸。

### 公共代码中的角度单位风险

仓库公共 `Transforms.updatePerspective` 将 `camera.fov` 直接交给 gl-matrix，而 Camera 默认值写作 45。当前 gl-matrix 接口需要弧度；因此必须在数据边界统一。推荐属性名 `fovRadians`，GUI 显示时转成度；或在调用处明确 `glMatrix.toRadian(camera.fovDegrees)`。不要靠“画面似乎还能出现”判断正确。

### resize 的完整处理

获取 CSS 尺寸乘 `devicePixelRatio`，只在变化时更新 drawing buffer；随后 `gl.viewport(0,0,width,height)`，重算 aspect/P。若使用与 canvas 同尺寸的 FBO，还要重建颜色/深度附件。

### 验收

在不同 Z 放两个同尺寸立方体：透视模式应大小不同，正交模式应相同。将窗口改成极宽，若圆仍为圆说明 aspect 正确。用 45° 与 `Math.PI/4` 对照应完全一致；直接传 45 若画面异常即可确认单位错误。
