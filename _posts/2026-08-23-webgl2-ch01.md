## 01：Canvas到底创建了什么

[查看原始示例](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch01/ch01_01_canvas.html)

### 1. 先预测运行结果

打开页面后会看到一个带蓝色虚线边框的矩形，内部通常呈现页面背景色。这里没有任何WebGL输出。蓝色边框由CSS布局/绘制系统生成，不是Canvas像素，也没有GPU shader参与。

这一区分很重要：浏览器本身也会使用GPU合成页面，但“浏览器可能用GPU绘制CSS”不等于“你的WebGL程序已经创建并使用WebGL上下文”。

### 2. HTML解析过程

浏览器从上到下解析文档。`<head>`里的title改变标签页标题；favicon link请求图标；style规则匹配所有canvas元素并添加5 CSS像素的蓝色点状边框。

解析到：

```html
<canvas id="webgl-canvas" width="800" height="600">
```

浏览器创建 `HTMLCanvasElement` DOM对象，并根据width/height内容属性建立800×600的绘图缓冲尺寸。这里的“绘图缓冲尺寸”是Canvas内部坐标系分辨率，不包括5像素边框。

此时Canvas还没有选择渲染上下文。Canvas可以取得2D、WebGL、WebGL2、bitmaprenderer等上下文，但同一Canvas建立一种主要上下文后不能随意换成另一种。

### 3. 三类尺寸逐一分清

#### 3.1 内容属性 `canvas.width/height`

决定内部缓冲分辨率。800×600意味着最多有480,000个像素位置，每个位置最终可保存颜色等信息，具体附件由上下文决定。

修改 `canvas.width`不仅是改一个数字。浏览器会重新分配绘图缓冲，并清空已有内容及部分绘图状态。不要在每帧无条件重复赋相同尺寸。

#### 3.2 CSS尺寸 `clientWidth/clientHeight`

决定Canvas在网页布局中显示多大。若CSS设置400×300，而内部仍800×600，浏览器把800×600结果缩放到400×300显示。清晰但像素密度更高；反向放大则会模糊。

#### 3.3 设备像素

高DPI屏幕一个CSS像素可能对应2×2或更多物理像素。`devicePixelRatio=2`时，为获得清晰画面，常把drawing buffer设为CSS尺寸的2倍。例如CSS 400×300，对应buffer 800×600。

像素数量按比例平方增长：DPR从1到2，片元数量可能变为4倍。因此常限制最大DPR。

### 4. Canvas为何看起来是白色

未绘制的Canvas默认透明。页面body背景通常白色，所以透过透明Canvas看见白色。把body设为红色，Canvas内部也会看起来红，但这仍不是Canvas保存了红色像素。

判断方法：给Canvas CSS背景色和body不同颜色，再截取Canvas像素或取得上下文清屏。CSS background位于Canvas位图背后，WebGL清屏色会成为Canvas位图内容。

### 5. 标签内部的英文什么时候显示

`Your browser does not support...`是fallback content。支持Canvas的现代浏览器不会把它画进Canvas。它不是错误提示UI。如果浏览器支持Canvas但不支持WebGL2，这段文字仍不会出现，所以必须在JavaScript检查 `getContext('webgl2')`。

### 6. 可复现实验

在Console运行：

```js
const c = document.querySelector('canvas');
console.table({
  width: c.width,
  height: c.height,
  clientWidth: c.clientWidth,
  clientHeight: c.clientHeight,
  rectWidth: c.getBoundingClientRect().width,
  rectHeight: c.getBoundingClientRect().height,
  dpr: devicePixelRatio
});
```

`getBoundingClientRect`包含变换后的CSS边界信息，鼠标拾取时比手工累计offset更可靠。client尺寸通常不包含边框，rect会反映实际边界；精确差异受box sizing影响。

接着执行 `c.style.width='1200px'; c.style.height='300px'`。内部比例仍4:3，显示比例变4:1；未来画圆会显示成横向椭圆。问题不是shader，而是显示映射比例。

### 7. 本示例尚未发生的事情

没有调用 `getContext`；没有默认WebGL framebuffer；没有shader/program；没有VBO/VAO/texture；没有clear或draw；没有动画循环。因此任何WebGL API问题都不可能在这个示例发生。

### 8. 掌握检查与答案

问：蓝色边框能证明WebGL2可用吗？不能，它是CSS。

问：把CSS尺寸改为两倍会增加Canvas内部像素吗？不会，除非同时修改width/height属性。

问：为什么DPR=2时通常需要4倍像素？宽和高都乘2，面积乘4。

问：修改width为何可能清空画面？因为这会重新建立Canvas绘图缓冲，而不是只改变布局属性。

## 02：取得WebGL2上下文

[查看原始示例](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch01/ch01_02_context.html)

### 1. 本例比上例增加了什么

Canvas本身未变。新增一段JavaScript，在页面完全加载后查找Canvas，并请求名为`webgl2`的上下文。运行结果是alert提示成功或失败，画面依然没有自定义绘制。

### 2. `'use strict'`

严格模式让某些原本静默的问题变为错误，例如意外给未声明变量赋值。它影响JavaScript语义，不改变WebGL。ES Modules默认严格模式，现代`<script type="module">`不必再写。

### 3. `window.onload = init`

脚本位于head。浏览器解析到脚本时，body里的Canvas尚未必存在。如果立即执行 `getElementById`，可能得到null。把函数注册给load事件，浏览器会在DOM和外部资源加载结束后调用。

`window.onload =`会覆盖此前赋给同一属性的handler。现代写法可用：

```js
window.addEventListener('load', init, { once: true });
```

或把module script放在body末尾/使用defer。仅依赖DOM时不必等待所有图片。

### 4. 查找Canvas并做守卫

```js
const canvas = document.getElementById('webgl-canvas');
```

DOM查询返回元素或null。示例先检查 `if (!canvas)`并return。没有这个守卫，下一句会因为对null调用getContext抛JavaScript TypeError。那是DOM问题，不是WebGL不支持。

更严格还应检查对象类型，因为页面可能存在同id的非Canvas元素：

```js
if (!(canvas instanceof HTMLCanvasElement)) {
  throw new TypeError('webgl-canvas 不是 Canvas');
}
```

### 5. `getContext('webgl2')`到底做什么

浏览器尝试为该Canvas创建WebGL2渲染上下文。成功返回 `WebGL2RenderingContext`，失败返回null。可能失败的原因包括浏览器/GPU不支持、用户/策略禁用硬件加速、上下文数量或资源受限等。

创建成功后，浏览器建立一套上下文状态和默认绘制目标。它并未自动创建用户shader、模型buffer或纹理。把context理解为“GPU渲染器”也不够精确；它是WebGL状态机和命令接口。

### 6. 可选上下文属性

```js
canvas.getContext('webgl2', {
  alpha: false,
  antialias: true,
  depth: true,
  stencil: false,
  premultipliedAlpha: true,
  preserveDrawingBuffer: false,
  powerPreference: 'high-performance'
});
```

这些是请求，不保证完全满足。用 `gl.getContextAttributes()`查看实际配置。

`preserveDrawingBuffer:true`常被误用来截图，它可能妨碍浏览器优化。更好的截图策略是在需要时把场景重画后读取/导出。

`alpha:false`表示页面合成时不需要Canvas alpha通道语义，可减少某些合成成本；它与片元shader是否可以输出alpha不是完全同一层问题。

### 7. Context与资源归属

以后由gl创建的buffer、texture、program等都属于这个context。另一个Canvas的context不能直接绑定这些对象。JavaScript变量只是对WebGL对象句柄的引用；实际资源由浏览器/驱动管理。

同一个Canvas再次请求`webgl2`通常返回同一上下文。若先成功取得2D context，再请求WebGL2，通常返回null，因为渲染模式已经确定。

### 8. 默认状态示例

创建后可以查询：

```js
console.log(gl.getParameter(gl.VERSION));
console.log(gl.getParameter(gl.SHADING_LANGUAGE_VERSION));
console.log(gl.getParameter(gl.COLOR_CLEAR_VALUE));
console.log(gl.getParameter(gl.VIEWPORT));
console.log(gl.isEnabled(gl.DEPTH_TEST));
```

典型clear color为(0,0,0,0)，depth test默认关闭。不要依赖教程记忆来推断所有状态；程序应在pass开始明确设置需要的状态。

查询驱动状态可能导致同步开销，所以初始化/调试可用，不应在每个对象每帧频繁调用。

### 9. Alert逻辑

三元表达式只把gl真假转换成文字。alert会阻塞页面主线程直到关闭，教学中醒目，实时渲染项目不应使用。可以把错误写入DOM并停止初始化。

### 10. Context loss

成功取得context不意味着永远有效。GPU重置、系统资源压力等可能触发`webglcontextlost`。监听事件、`preventDefault`并在restore后重建所有GPU资源，是稳健应用的一部分。JavaScript还保存着旧句柄不代表GPU内容仍存在。

### 11. 错误因果链

Canvas id错 → DOM查询null → 守卫输出“找不到Canvas”。

Canvas存在但WebGL2不可用 → getContext返回null → 进入失败alert。

Context成功但屏幕仍白 → 正常，因为没有clear/draw；白色来自页面背景。

这三种现象必须分开，不能都归为“WebGL黑屏”。

### 12. 现代初始化函数

```js
function createWebGL2Context(canvas) {
  if (!(canvas instanceof HTMLCanvasElement)) {
    throw new TypeError('需要 HTMLCanvasElement');
  }
  const gl = canvas.getContext('webgl2', { antialias: true });
  if (!gl) throw new Error('无法创建 WebGL2 上下文');
  return gl;
}
```

调用者通过try/catch决定显示错误页还是降级；函数不alert、不返回含糊undefined。

## 03：状态机、清屏色与键盘事件

[查看原始示例](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch01/ch01_03_attributes.html)

### 1. 本例真正的主题

表面功能是按1变绿、按2变蓝、按3随机、按4显示清屏色。深层主题是WebGL“状态设置”和“执行命令”分离：`clearColor`只改变状态，`clear`才读取该状态并修改绘制目标。

以后大量API遵循相同模式：bindBuffer选择当前对象，bufferData操作当前对象；useProgram选择程序，uniform/draw使用当前程序；activeTexture选择单元，bindTexture修改该单元绑定。

### 2. 为什么gl变成全局变量

上一例gl只在init内部使用。本例按键发生在init结束以后，`checkKey`仍需访问gl，所以示例把它声明为脚本作用域的`let gl`。

执行顺序：页面load调用init；init给全局gl赋值并注册keydown；init返回；以后每次按键由浏览器事件循环调用checkKey，闭包/外层作用域仍能找到gl。

全局依赖便于教学，却让函数不可复用。更好的写法：

```js
function createKeyHandler(gl) {
  return event => { /* 使用传入的 gl */ };
}
window.addEventListener('keydown', createKeyHandler(gl));
```

### 3. Rest参数与Spread参数

函数声明 `updateClearColor(...color)`把所有实参收集为数组。例如调用四个数字后，color为长度4的普通数组。

调用 `gl.clearColor(...color)`又把数组展开为四个独立参数。这是JavaScript语法糖，不是WebGL功能。直接声明 `(r,g,b,a)`会更显式；数组形式便于GUI传色。

若传三个数字，alpha变undefined，WebIDL数值转换可能产生非预期/错误状态；函数应验证长度和有限范围。

### 4. `gl.clearColor`

执行前：context保存某个COLOR_CLEAR_VALUE，默认常为(0,0,0,0)。

执行：四个JS number转换为GL浮点并被钳制/保存到对应状态。

执行后：COLOR_CLEAR_VALUE改变；颜色缓冲内容没有改变；Canvas画面也不必改变。

这就像设置“下一次擦黑板用什么颜色”，并没有真正擦黑板。

### 5. `gl.clear(gl.COLOR_BUFFER_BIT)`

`COLOR_BUFFER_BIT`是位标志。clear的mask可组合：

```js
gl.clear(gl.COLOR_BUFFER_BIT | gl.DEPTH_BUFFER_BIT);
```

调用时读取当前clear color，将当前draw framebuffer的启用颜色附件清成该值。命令提交到WebGL实现；浏览器/驱动可延迟真正GPU执行，但API顺序语义必须保持。

默认draw framebuffer属于Canvas。以后绑定自建FBO后，相同clear会清FBO而不是Canvas。因此“clear清Canvas”只是当前绑定目标的结果。

### 6. clear受哪些状态影响

Clear不受viewport限制，所以即使下一行把viewport设0×0，已经执行的clear仍覆盖整个可清区域。

Clear会受SCISSOR_TEST影响。若开启scissor并设矩形，只清矩形内。颜色写掩码也会影响颜色分量是否可写；depthMask影响深度清理写入。

这解释了为什么复杂程序中clear只清一角时，应检查scissor状态，而不是viewport。

### 7. 源码中的零viewport问题

```js
gl.viewport(0, 0, 0, 0);
```

Viewport定义把NDC映射到窗口像素的矩形。宽高为0意味着所有未来光栅化输出被映射到零面积区域，不会产生正常片元。

为什么本例看起来仍正确？因为它只执行clear，没有执行draw。Clear不依赖viewport。这个错误像一颗延迟炸弹：下一章加入三角形后会黑屏，却容易错误怀疑shader或buffer。

正确值通常为：

```js
gl.viewport(0, 0, gl.drawingBufferWidth, gl.drawingBufferHeight);
```

`gl.canvas.width`通常相同，但drawingBuffer尺寸更直接表达实际目标。

### 8. `checkKey`的事件流

浏览器产生KeyboardEvent并传入回调。示例读取已废弃的`event.keyCode`：49–52对应主键盘数字1–4。现代写法用`event.key`，它表达用户输入字符；需要物理按键位置则用`event.code`如`Digit1`。

Switch每个case用额外花括号创建块作用域，允许在不同case声明同名const而不冲突。

### 9. 随机颜色

Math.random返回[0,1)伪随机数，正好落入颜色通道范围。它生成的是数值RGB，不考虑人眼均匀性或sRGB/线性空间。这里仅演示状态变化。

Alpha固定1，意味着清屏像素不透明。最终与页面合成还受context alpha属性和浏览器合成规则影响。

### 10. 查询COLOR_CLEAR_VALUE

```js
const color = gl.getParameter(gl.COLOR_CLEAR_VALUE);
```

返回类似Float32Array的四分量值。它读取的是clear状态，不是屏幕某像素。即使删除clear、画面仍旧，它也会显示新clearColor。

读取Canvas像素需要`readPixels`，那是完全不同的操作，而且可能同步等待GPU。

`toFixed(1)`只格式化显示。传入0.2后内部Float32可能是0.20000000298之类，因为二进制浮点不能精确表示很多十进制小数。

### 11. `window.focus()`为什么出现

Alert关闭后示例尝试把焦点还给window，确保继续收键盘。现代浏览器对程序化focus有安全/用户体验限制。更合理是让Canvas可聚焦、在Canvas监听输入，并提供可见焦点样式。

### 12. 一次按键的逐时刻状态

按数字1之前：clear value可能默认黑透明；Canvas透明/旧色；viewport为初始尺寸。

调用clearColor后：clear value=(.2,.8,.2,1)；Canvas仍旧。

调用clear后：默认颜色附件变绿；clear value保持绿色。

调用viewport后：Canvas仍绿；viewport变0×0；未来draw受影响。

按4：query返回绿色；不读取Canvas；不修改GPU绘制内容。

### 13. 三个容易混淆的实验

#### 实验A：设置但不执行

注释clear。按键后按4显示颜色已变，画面不变。结论：状态和buffer内容分离。

#### 实验B：执行顺序

把clear放在clearColor前。第一次按1会用旧颜色清屏，然后把“下次”颜色设绿；第二次按另一个键时才看到上一次颜色。结论：命令读取调用当时状态。

#### 实验C：Viewport延迟影响

保持0×0 viewport，加入下一章三角形draw。背景能clear，三角形不见。恢复viewport后立刻出现。结论：不同命令读取不同状态子集。

### 14. WebGL错误检查

这些合法调用通常不产生错误。故意给clear传非法mask后可调用：

```js
const err = gl.getError();
```

WebGL常把错误记录到error flag而非抛JS异常。`getError`读取并清除一个错误。它适合教学/调试；逐调用查询会产生开销，生产可使用调试包装器或浏览器工具。

### 15. 改写后的实现

```js
function setBackground(gl, rgba) {
  if (rgba.length !== 4 || rgba.some(v => !Number.isFinite(v))) {
    throw new TypeError('rgba 必须是4个有限数字');
  }
  gl.clearColor(...rgba);
  gl.clear(gl.COLOR_BUFFER_BIT);
}

window.addEventListener('keydown', event => {
  if (event.key === '1') setBackground(gl, [.2,.8,.2,1]);
});
```

Viewport不应藏在“更新背景色”函数内，因为它与背景色职责无关。把无关状态修改混入函数是状态泄漏的重要来源。

### 16. 掌握检查

为什么查询clear value不能证明Canvas像素已经变色？因为它查询状态，不查询颜色附件。

为什么0×0 viewport没有破坏清屏？clear不读取viewport状态。

为什么应把viewport调用移出updateClearColor？它是帧目标尺寸状态，与颜色更新没有内聚关系。

为什么WebGL错误可能没有try/catch异常？WebGL API常记录GL错误状态或shader日志，而非抛JavaScript异常。

## 04：汽车展厅完整程序预览

[查看原始示例](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch01/ch01_04_showroom.html)

### 1. 为什么第一章突然出现复杂程序

前三个示例只创建上下文和清屏，第四个却包含四盏灯、汽车模型、相机、GUI和十多个公共类。它不是要求初学者立即掌握全部细节，而是给出全书终点，让后续章节有明确坐标。

阅读大型渲染程序时不要从第一行一直向下死磕。先找入口，再沿调用图展开：

```text
window.onload
  └─ init
      ├─ configure
      │   ├─ Canvas / GL状态
      │   ├─ Program接口
      │   ├─ Scene / Clock
      │   ├─ Camera / Controls / Transforms
      │   └─ Lights / Floor / 车型描述
      ├─ load
      │   ├─ goHome
      │   └─ loadCar（异步启动178个part）
      ├─ clock.on('tick', draw)
      └─ initControls
```

### 2. 外部依赖为何有加载顺序

dat.gui提供右上控制面板；gl-matrix提供vec/mat运算。后面的公共脚本通过普通script在全局声明类，所以顺序必须满足依赖：Clock继承EventEmitter，Transforms依赖gl-matrix和Camera数据，Scene会创建Texture并调用utils。

普通script全局依赖没有模块图，漏一个文件会在运行时出现`X is not defined`。现代ES Modules会显式import，构建工具能更早发现依赖问题。

### 3. 顶点shader的输入与输出

`numLights=4`是编译期常量。WebGL shader循环常需要可确定上限，以利编译器展开。

三个矩阵：ModelView把模型顶点移到观察空间；Projection从观察空间到裁剪空间；NormalMatrix用于法线。

两个attribute：position和normal。它们由当前VAO描述的数据源逐顶点提供。

输出：一个normal、四个light ray、四个eye向量。光栅器会把它们在三角形内插值后交给片元shader。

### 4. 顶点位置的两个用途

```glsl
vec4 vertex = uModelViewMatrix * vec4(aVertexPosition, 1.0);
```

这里得到观察空间位置。w=1表示位置，允许平移生效。

```glsl
gl_Position = uProjectionMatrix * uModelViewMatrix * vec4(...);
```

得到裁剪空间位置，交给GPU裁剪、透视除法和viewport映射。可以复用前面的vertex写成`uProjectionMatrix * vertex`，减少重复矩阵乘法；编译器可能优化，但源码表达可更清楚。

### 5. Light ray的方向约定

源码写：

```glsl
vLightRay[i] = vertex.xyz - lightPosition.xyz;
```

它得到“从光源指向表面”的向量。片元shader漫反射使用`dot(normal,-light)`，先取负得到“从表面指向光源”，因此符号在数学上配套。

但这里存在更重要的空间问题：vertex已经乘ModelView处在观察空间，uLightPosition由JavaScript直接上传看似世界坐标，没有在shader中乘View。若两者空间不同，相减没有几何意义，灯会随相机产生不正确行为。

正确方法之一是在CPU把所有世界灯位置乘View后上传；或上传View矩阵，在shader中变换灯；或让所有计算统一在世界空间。变量名应写`lightPositionVS`提醒空间。

### 6. Eye向量为何重复四次

观察空间相机在原点，所以从表面指向眼睛为`-vertex.xyz`。它与灯数量无关，但源码在每盏灯循环中重复写入`vEye[i]`，四个值相同。

功能上可运行，结构上浪费varying带宽。应该只输出一个`vEye`，片元对所有灯复用。

### 7. 法线变换的细节

```glsl
vNormal = vec3(uNormalMatrix * vec4(aVertexNormal, 1.0));
```

方向向量语义应使用w=0。标准4×4逆转置仿射矩阵的平移通常落在不影响xyz的位置，因此该写法可能看似正常，但概念不严谨，也可能给后续扩展带来问题。推荐`vec4(normal,0.0)`或使用mat3 normal matrix。

法线没有在顶点shader normalize，片元shader会normalize插值后的值。这是必要的，因为插值会改变长度。

### 8. 片元shader的快速分支

如果wireframe或illum=0，直接输出Kd和透明度d并return。这样线框不计算复杂光照，illum 0表示无光照材质。

注意输出alpha不等于产生透明。configure只设置blendFunc，却没有`enable(BLEND)`，所以常规几何仍直接覆盖颜色缓冲。这个例子的d更多是数据传递预览。

### 9. Illum 1：漫反射

每盏灯：归一化light ray；再次归一化normal；计算`dot(normal,-light)`并clamp；乘灯漫反射uLd和材质uKd；累加。

Normal在循环外已经normalize一次，循环内重复normalize是多余计算。可以提到循环外。

没有ambient项；暗面可能完全黑。四盏灯贡献直接相加，默认8位颜色附件最终会钳制，高亮可能饱和。

### 10. Illum 2：漫反射加镜面

Eye/light归一化。`reflect(light,normal)`传入的是入射向量（从光到表面），符合GLSL reflect的I约定。反射向量与eye点乘，高光指数uNs控制集中程度。

镜面项额外乘4.0是经验增亮，不是物理常数。代码没有显式要求N·L>0才计算镜面，因此某些背光几何可能出现不合理高光。更稳健应在漫反射为正时才加镜面。

### 11. Configure：Canvas和GL状态

`autoResizeCanvas`把Canvas属性设为window innerWidth/Height并监听resize，但没有乘DPR。画面在高DPI可能不够清晰。Resize还应触发FBO附件和projection更新；本例每帧updatePerspective。

GL状态：clearColor浅灰；clearDepth=1；开启DEPTH_TEST；depthFunc=LESS；设置标准alpha blend函数但没开启blend。

执行前后的关键状态：DEPTH_TEST从默认false变true；depth compare从默认LESS（通常本就LESS）显式设定；blend factors改变但BLEND enable仍false。

### 12. Program接口加载

Program编译/链接两shader并use。attributes数组还包含`aVertexColor`，但当前顶点shader未声明它，因此`getAttribLocation`会返回-1。Scene.add检查location>=0后才上传该属性，说明接口列表可以包含非活跃项，但这也可能隐藏拼写错误。

Uniform locations缓存到program对象。`uLightPosition`同时出现在两shader阶段但代表同一program uniform接口；片元shader声明后未直接使用，链接器的活跃判断要结合顶点阶段使用。

### 13. Clock创建时的时序

`new Clock()`构造时立刻调用tick并安排RAF，但此时draw listener尚未注册。第一次tick不会绘制；后续RAF在init完成后才emit给draw。功能可行，但“构造器启动异步循环”让生命周期隐式。更清晰是显式`clock.start()`。

### 14. Camera、Controls和Transforms

Camera选择ORBITING，Controls直接注册Canvas/Window事件。Transforms在构造时计算MV/P/Normal。

公共Transforms存在FOV单位需要审计：Camera默认fov=45，而gl-matrix perspective要求弧度。若没有在别处转换，projection会错误。不要因为最终画面“似乎能看”就忽略单位。

### 15. 四盏灯的数据布局

lightPositions对象保存四个世界位置。每个Light保存position、diffuse、specular；LightsManager.getArray展平：

```text
positions = [x0,y0,z0, x1,y1,z1, x2,y2,z2, x3,y3,z3]
diffuse  = [r0,g0,b0, r1,g1,b1, ...]
```

`uniform3fv`一次上传整个数组。Shader的数组长度固定4，CPU数组必须提供足够连续分量。

### 16. Floor和车型描述

Floor在CPU生成线网格，加入Scene后和模型对象共享绘制流程。它的wireframe=true，因此draw走LINES。

CarModelData不是几何，只是加载描述：paint alias、178个part、URL前缀。每part最终由Scene.load获取JSON。

### 17. `loadCar`的资源问题

`scene.objects=[]`直接丢弃对象列表，但没有delete旧VAO/VBO/IBO。如果重复调用，会造成GPU资源泄漏。当前页面主要调用一次，所以不明显。

Scene.add(floor)，再loadByParts启动178个异步fetch。loadByParts不返回整组Promise，本例没有明确“汽车加载完成”状态；部件会陆续加入并逐帧出现。

健壮版本应返回Promise.all、显示进度、检查response.ok，并为失败part提供错误。

### 18. Draw：Frame级工作

每个tick首先viewport匹配Canvas，然后清颜色和深度。Depth必须每帧清，否则上一帧深度会遮挡新帧。

`updatePerspective`每帧重算P，即便尺寸/FOV没变，教学简单但可用dirty flag优化。

Try/catch只能捕获同步JavaScript异常，不能把shader编译日志、GL error或之前异步fetch rejection自动变成异常。

### 19. Draw：Object级工作

Scene.traverse逐对象。不可见就`return`，回调返回undefined，Scene.traverse继续下一个对象。

每对象调用calculateModelView，但没有对象Model变换，所以实际只取Camera view。Push/set/pop看起来像矩阵栈演示，此处没有在push后修改矩阵，push/pop是冗余框架结构。

接着上传Ka/Kd/Ks/Ns/d/illum。这是每part材质状态。然后bind VAO和IBO。

公共Scene.add先绑定IBO再绑定对象VAO，未把EBO正确封入该VAO；draw这里显式bind IBO补救。因此VAO并非完整自包含。这是代码审计中非常重要的绑定顺序问题。

### 20. Lines并不等于真正线框

若wireframe，drawElements使用LINES，但indices原本按三角形三元组组织。LINES会每两个索引成一条线，不会自动把每个三角形三条边正确展开；可能缺边、连接错误或显示内部边。

真正线框可在CPU从三角索引提取无向边集合，或为三角形加入barycentric坐标在片元shader画边。

### 21. Unbind的意义

每对象后解绑VAO和buffer。解绑不是绘制正确性的硬要求；下一对象会覆盖绑定。教学中能减少意外状态依赖，性能渲染器通常缓存当前状态、避免无意义解绑。

在bindVertexArray(null)后解绑ELEMENT_ARRAY_BUFFER影响默认VAO，不影响刚解绑对象VAO；但由于对象VAO本来未捕获EBO，下一帧仍靠显式bind。

### 22. GUI回调的真实效果

Color将0–255 GUI色归一化，遍历alias包含paint的部件并改Kd。下一帧draw上传新Kd。

名为Shininess的控件实际上把`item.Ks=[v,v,v]`，改变镜面颜色/强度，而不是高光指数Ns。真正shininess通常应改Ns。这是命名与行为不一致。

灯GUI直接修改Light对象，并立刻`gl.uniform3fv`。它假设当前program仍是展厅program；如果未来有多program，这种GUI直传GPU会脆弱。更好是只改state，render统一上传。

Background只改clearColor状态，下一tick clear时生效。Floor改visible，draw会跳过。Go Home调用Camera方法恢复视角。

### 23. `eachCarPanel`与`~indexOf`

`~item.alias.indexOf(paintAlias)`利用位取反：index=-1时~-1=0为false，其他索引得到非零为true。这是旧技巧，`includes(paintAlias)`更可读。

Scene.traverse会在回调返回非undefined时提前break；这里回调没有显式return，能遍历所有part。若cb意外返回值，可能提前停止，接口契约不直观。

### 24. 一帧的CPU→GPU提交清单

Frame：viewport、clear、projection计算。

每对象：3个矩阵uniform；Ka/Kd/Ks三个vec3；Ns/d两个float；illum/wireframe两个int/bool；VAO/EBO绑定；一个drawElements。

178个汽车part意味着至少约178次draw和大量uniform调用。GPU三角形可能不是瓶颈，CPU状态提交也可能成为瓶颈。

### 25. 建议的调试拆分

第一步只画Floor，确认Camera/P。第二步加载一个part，片元固定洋红。第三步输出normal颜色。第四步只漫反射一盏灯。第五步四灯。第六步镜面和材质。最后GUI。

如果直接面对最终黑屏，资源、矩阵、法线、灯、材质、状态六个维度同时存在，定位成本很高。

### 26. 本例发现的问题汇总

- Light位置与vertex可能不在同一空间。
- Eye varying按灯重复。
- Normal方向语义使用w=1。
- Normal在灯循环重复normalize。
- Blend函数设置但未开启BLEND。
- aVertexColor接口不存在，location=-1。
- FOV度/弧度风险。
- loadByParts缺ready Promise；重载会泄漏。
- Scene.add的EBO未在对象VAO绑定时配置。
- LINES不是正确三角网格线框。
- GUI Shininess实际修改Ks而非Ns。
- GUI直接上传uniform依赖current program。

这些并不意味着示例毫无价值；恰恰说明教学代码要同时学习“机制”和“代码审计”，不能把final画面当作最佳实践证明。

### 1. 为什么必须做对照阅读

完成版的价值不是“以后只看final”，而是让你通过diff识别作者希望修正的行为。运行：

```bash
diff -u book-code/ch01/ch01_03_attributes.html \
        book-code/ch01/ch01_05_attributes-final.html
```

把差异分三类：只改注释/格式；修复行为；仍保留的教学简化。没有行为变化的代码不应被误判为新WebGL知识。

本仓库的final主要把手写Canvas/context检查替换成`utils.getCanvas`和`utils.getGLContext`，并引入normalize.css；键盘逻辑和`viewport(0,0,0,0)`仍然保留。因此“final”没有修复零viewport，也没有改用event.key。它表示书中该小节代码整理完成，不表示经过现代工程审计。

### 2. 重新检查五层状态

DOM层：Canvas是否存在，尺寸是什么。

JavaScript层：事件何时调用，gl作用域是否有效。

Context状态层：clear color、viewport等当前值。

Framebuffer内容层：clear是否真正写入颜色附件。

页面合成层：Canvas alpha、CSS背景和浏览器怎样组合。

遇到“颜色不对”时，必须先判断问题在哪一层。

### 3. 本章完整项目要求

新建一个独立页面，不复制原例结构，实现：全屏Canvas；DPR适配但最大2；WebGL2失败时DOM错误提示；数字键切色；页面显示当前clear state、drawing buffer尺寸和viewport；窗口resize自动更新；监听context loss；无alert、keyCode或全局gl。

### 4. 推荐结构

```text
main
  ├─ findCanvas
  ├─ createContext
  ├─ createAppState
  ├─ registerInput
  ├─ registerResize/context events
  └─ requestAnimationFrame(frame)

frame
  ├─ resizeIfNeeded
  ├─ viewport
  ├─ clearColor(state.background)
  ├─ clear
  └─ updateDebugPanel
```

State由JavaScript持有，render把state提交给gl。不要为了显示clear color每帧getParameter；你自己刚设置的值应在state中已有。调试按钮可额外query验证两者一致。

### 5. Resize实现解释

读取client尺寸乘DPR并round。只有新尺寸不同才赋canvas.width/height，因为赋值会重置buffer。之后viewport使用drawingBufferWidth/Height。由于本章没有透视矩阵，不需更新aspect；下一章起必须一起更新。

### 6. Context loss实现解释

监听`webglcontextlost`并preventDefault，暂停RAF/标记不可绘制。监听restored后重新取得/使用context并重建资源。本章只有状态，没有复杂buffer；下一章起所有shader/program/VAO/texture都要重建。

### 7. 验收测试

普通DPR=1与高DPI都清晰；改变窗口尺寸无拉伸；快速连按键画面和state一致；手工模拟context loss（通过扩展/工具）后页面不继续盲目draw；恢复后可重新清屏；Console无错误。

### 8. 本章最终口述题

完整描述按键1发生后，从KeyboardEvent到Canvas变绿的链条：事件循环调用handler；handler改变应用state；render调用clearColor改变context state；clear读取该状态并清当前draw framebuffer颜色附件；浏览器把Canvas位图与页面合成；屏幕显示绿色。

如果能清楚区分每个阶段，并解释0×0 viewport为什么不影响clear但影响draw，就真正完成了第一章。
