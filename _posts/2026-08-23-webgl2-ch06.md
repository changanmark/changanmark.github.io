## 6.1 顶点色、材质色与 Alpha

[源码：ch06_01_cube.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch06/ch06_01_cube.html)

本例用三个开关分离概念：`uUseVertexColor` 选择 attribute 顶点色或 uniform 材质色；`uUseLambert` 决定是否乘漫反射项；`uAlpha` 只决定 shader 输出的 alpha。

attribute 随顶点读取，并在三角形内部透视正确插值；uniform 在一次 draw 内对所有顶点相同。若顶点色 RGB 分别放在三角形三个角，片元颜色是重心权重组合，并非自动做色彩管理。

Lambert 为 `max(dot(N,L),0)`。N、L 必须 normalize 且同处 eye/world 任一空间。负点积表示光在表面背面，clamp 防止产生负光。

### Alpha 不等于透明

默认禁用 BLEND，片元 `(r,g,b,0.2)` 仍直接覆盖 framebuffer 的 RGB；alpha 只是被写进目标 alpha 通道。源码注释给出启用 BLEND 与标准函数，但还需要考虑深度写和绘制顺序。

标准非预乘混合：

```text
Cout = Csrc·Asrc + Cdst·(1-Asrc)
```

半透明红覆盖蓝，Asrc=.25 时得到 `(0.25,0,0.75)`。反过来画结果不同，说明 alpha blending 不可交换。

源码 `DEPTH_TEST + LESS` 对不透明立方体合理。调试时分别：只改 alpha、再开 BLEND、再旋转观察前后面，记录每一步是 shader 输出变化还是固定管线状态变化。

## 6.2 双光源墙面：独立 Uniform

[源码：ch06_02_wall-initial.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch06/ch06_02_wall-initial.html)

红灯和绿灯分别拥有 `uPositionRedLight/uDiffuseRedLight` 与绿色对应变量。顶点 shader 计算观察空间顶点、法线及两条 light ray；片元 shader 分别算 Lambert contribution 后相加。

这种写法直观但不可扩展：加一盏灯需要同步修改 GLSL 声明、varying、计算分支、JS location 列表和上传代码。下一节加入蓝灯正是让重复成本暴露出来。

`uLightSource` 用于绘制代表灯的小球：代理球应显示自身 diffuse，不再按同一灯给自己做受光计算。代理几何的位置和真正 uniform 位置必须来自同一数据源，否则画面会“球在 A、光从 B 来”。

源码启用了 BLEND、设置 FUNC_ADD，却没有在此处设置 blendFunc；默认因子是 ONE/ZERO，实际仍近似覆盖。`blendEquation` 只决定加/减/min/max，不能代替 source/destination factor。

片元中的 cutoff 实际比较 Lambert `N·L`，它筛掉的是表面入射角较斜的区域，不是光源锥角。验收时单独关闭一灯，把每灯贡献输出为灰度；统计加第三灯需改多少位置，理解数组化动机。

### 执行链与状态恢复

configure 建 program 后一次上传两灯位置/颜色和 cutoff；load 异步加入墙、灯代理等对象；tick 中更新 P/MV/N，代理对象用 `uLightSource=true` 直接显示材质，墙则恢复 false 后累计光照。`uLightSource`、material、wireframe 都是 program uniform 状态，必须每个对象明确赋值。

GPU 对每顶点计算两条 light ray 并插值到片元，片元循环展开为两个独立分支。开 BLEND 但默认 ONE/ZERO 不会把不同灯的 draw 相加；三灯贡献是在单个 shader invocation 内相加。把 blend 完全 disable 后光照结果应不变，可验证这一区别。

## 6.3 三光源墙面

[源码：ch06_03_wall-final.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch06/ch06_03_wall-final.html)

本例按上一节的模式加入蓝灯。`finalColor = red + green + blue` 展示加性光照：不同通道叠加能形成黄、青、品红和白。

默认 framebuffer 通常是归一化 8-bit，写入超过 1 的通道会 clamp，强光区域会丢失层次。这不是“物理能量自动曝光”。HDR 管线应渲染到浮点颜色附件，再 tone mapping 到显示范围，并在正确线性色彩空间做光照。

环境光 `Ia` 在源码中可能计算却未合入最终输出，应逐行检查实际赋值，不能因变量存在就认为生效。GLSL 优化器还会移除未参与输出的 uniform，导致 `getUniformLocation` 返回 null；对 null 调 uniform 是无操作。

该例依然开启 BLEND 但缺显式 blendFunc；不应把“灯光 contribution 相加”与“framebuffer 混合”混为一谈：前者发生在同一 fragment shader 内，后者发生在不同 draw 的片元输出与已有目标颜色之间。

验收：逐灯上传纯红/绿/蓝，将 contribution 可视化；把三个强度都设 1，检查饱和；然后把每灯结构改成数组，列出被删除的重复代码。

### 从 CPU 到片元

JS 分别保存三灯数据并向六组 position/diffuse uniform 上传；顶点阶段产生三组 varying；片元阶段做三次 normalize/dot/threshold/add。新增一灯同时增加 uniform 与 varying 压力，而 draw call 数不变。

现代改写先定义 `Light { positionEye, diffuse }` 的统一布局，再用固定上限数组和 count；灯数据只在灯/Camera 变化时上传。用浮点 FBO+tone map 才能观察超过 1 的线性亮度，默认 framebuffer 的 clamp 不能作为光照上限设计。

## 6.4 光源 Uniform 数组

[源码：ch06_04_wall-light-arrays.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch06/ch06_04_wall-light-arrays.html)

shader 用编译期常量 `numLights=3` 声明 `vec3 uLightPosition[3]`、`vec4 uLightDiffuse[3]`，并在固定循环中计算。JS 的 `LightsManager.getArray('position')` 把对象数组展平为 `x0,y0,z0,x1,y1,z1...`，一次 `uniform3fv` 上传；颜色同理以 RGBA 连续排列。

uniform API 接受 typed array 或扁平 array，不会递归理解 `[[x,y,z],...]`。数组 location 通常可由基础名或 `[0]` 取得，但包装层应检查 null 并以实际链接 program 为准。

固定上限方便编译器展开，却受 `MAX_VERTEX_UNIFORM_VECTORS` / `MAX_FRAGMENT_UNIFORM_VECTORS` 限制。每灯跨顶点到片元传多个 varying 也受分量上限。规模增大可用 uniform block、浮点纹理保存灯数据，以及 forward+/tiled/clustered 只遍历影响当前区域的灯。

源码每个光源都构造 `vNormal[i]`，实际表面法线本可只传一次；重复数组浪费 varying。还应注意 normal/direction 是方向，齐次 w 应为 0，不是 1。

验收时打印展平数组长度：3 个 position 必须 9 项、3 个 diffuse 必须 12 项。交换数组中两盏灯的位置但不交换颜色，观察代理与光照是否失配。

### 上传与索引的逐项对应

一次 `uniform3fv(location,[p0x,p0y,p0z,p1x...])` 连续写数组元素 0、1、2；GLSL `for i` 用同一 i 访问 position/diffuse。代理 draw 也应从 LightsManager 的第 i 项读位置/颜色，这样可视几何与真实灯共享索引。

uniform array 属于 program，不属于 VAO。切换 program 后必须在新 program 上传自己的数组；仅重新 bind VAO 不会恢复。若灯在 world space，Camera 变化时 CPU 重新生成 eye-space数组或 shader 用 View 变换，不能对每对象乘不同 Model。

## 6.5 四光源数组完成版

[源码：ch06_05_wall-light-arrays-final.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch06/ch06_05_wall-light-arrays-final.html)

完成版把 `numLights` 增为 4，证明增加灯主要是追加数据，而非复制整套 shader 变量。但 GLSL 数组长度与 JS lightsData 数量仍是两个独立真相，必须同步；少传的 uniform 元素保留旧值/初始化值，循环却仍会访问，容易产生幽灵灯。

工程版可声明 `MAX_LIGHTS` 与 `uLightCount`，循环固定上限并在 `i>=count` 时退出；WebGL2 对循环和动态索引支持较好，但仍需测目标 GPU。更结构化可用 std140 UBO，同时要遵守 vec3 在结构体中的 16-byte 对齐，不能按紧密 12-byte 直觉打包。

代理球绘制时改变 material 和 `uLightSource`，随后画墙前必须恢复。uniform 是跨 draw 持久状态；若依赖 traverse 恰好顺序正确，换一份场景 JSON 就可能全墙显示为自发光。建议每个 pass/材质绑定函数完整声明其状态。

验收：将灯数量从 4 改 2，确保 shader count、上传长度与代理数量都一致；查询设备 uniform 上限，按每灯 vec4 消耗估算理论上限，再说明为何实际还要给相机/材质矩阵留空间。

### 一帧状态表

frame uniform：P/View、四灯 position/diffuse、ambient、cutoff；object uniform：MV/normal、material、wireframe/lightSource；VAO 状态：position/normal/EBO。按这个频率分组，可发现灯数组不应在每个墙 part 前重复上传。

完成版仍在 vertex shader 为每灯输出重复 normal，且 cutoff 仍是 Lambert threshold。现代化不是只把 JS 数组换 UBO，还要先修语义：单一 N/P varying，在 fragment 中由灯位置构造 L；真正 spotlight 另传 direction/cosOuter。

## 6.6 硬边“聚光”与源码审计

[源码：ch06_06_wall-spot-light.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch06/ch06_06_wall-spot-light.html)

这一例名为 spot light，但源码实际不是标准聚光模型。顶点 shader 算 `vNormal[i] = normal - directionLight`，片元再令 `lambertTerm=dot(normalize(vNormal),-normalize(vLightRay))` 并与 cutoff 比较。这是把光方向混入法线后做阈值，不是比较“光轴与光源到片元方向”的夹角。

严格聚光应先统一 eye space：

```glsl
vec3 toFragment = normalize(Peye - lightPosEye); // 光源 -> 片元
vec3 spotDir = normalize(lightDirEye);           // 光轴
float cosTheta = dot(toFragment, spotDir);
float inside = step(cosOuter, cosTheta);
vec3 L = normalize(lightPosEye - Peye);           // 片元 -> 光源
float lambert = max(dot(N, L), 0.0);
```

cutoff 应存余弦。30° 外锥对应 cos≈0.866；角越小，余弦越大，所以 `cosTheta >= cosOuter` 才在锥内。直接比较角度与余弦属于单位/量纲错误。

源码把 `uLightDirection` 同时在 vertex/fragment 声明，却主要通过改变后的 vNormal 间接使用；方向用 normal matrix 时齐次 w 应为 0。对于只含刚体 View，用 mat3(View) 转方向即可，不应乘对象 model。

硬 step 边界会产生突变和锯齿。先用颜色输出 `cosTheta` 灰度，再输出 mask，确认正负号；这是调试 spotlight 最可靠的顺序。

## 6.7 比例衰减

[源码：ch06_07_wall-spot-light-proportional.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch06/ch06_07_wall-spot-light-proportional.html)

与上一例相比，锥内 contribution 又乘 `lambertTerm`，所以阈值处从 0 突然跳到约 cutoff，仍不是从边缘平滑升起；变量依旧是经 `normal-direction` 构造后的点积，不是标准 spot angle。

如果要在内外锥间线性过渡，使用：

```glsl
float attenuation = clamp(
  (cosTheta - cosOuter) / (cosInner - cosOuter), 0.0, 1.0);
```

`cosInner > cosOuter`，两者相等会除零，GUI 必须约束或特殊处理。`smoothstep(cosOuter,cosInner,cosTheta)` 可让边界一阶更平滑。这里在 cos 空间线性，并非角度空间线性，但避免 acos，成本低且常用。

最终 diffuse 应把 spotlight attenuation 与表面 Lambert、距离衰减分别相乘：`lightColor * material * spot * max(N·L,0) * distanceAtten`。把它们拆开显示，才能知道边缘来自哪一项。

验收：固定表面正对灯，让 Lambert 恒接近 1，只观察 spot；再固定 spot=1，旋转表面只观察 Lambert。这样不会像原源码那样把两个角度效应混成一个数。

## 6.8 指数衰减

[源码：ch06_08_wall-spot-light-exponential.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch06/ch06_08_wall-spot-light-exponential.html)

源码去掉 cutoff 分支，对 `lambertTerm` 做 `pow(lambertTerm, exponentFactor*uCutOff)`。指数越大，0～1 中除接近 1 的值都迅速变小，于是光斑集中。

这里有两个数值风险：lambertTerm 可能为负；GLSL 对负底数的非整数幂结果未定义/NaN。应先 `max(value,0.0)`。其次 cutoff 被当指数乘子，而不是几何边界，因此 GUI 名称与数学含义不符。

标准实现可在内外锥 smoothstep 后再用 `pow(attenuation, exponent)` 调整形状；cutoff 控制范围，exponent 控制范围内分布，职责分离。再乘物理近似距离项 `1/(kc+kl·d+kq·d²)`，并避免分母接近 0。

指数 1、2、8、32 应做同屏曲线对照。若出现整片黑、闪烁或平台差异，先把 pow 输入输出分别着色，检查是否有负数/NaN，而不是盲调光强。

### CPU/GPU 时序与改写

configure 上传 cutoff/exponent，GUI callback 直接改 current program uniform；draw 对墙和灯代理共享 program。工程应把参数存 state，下帧 material/light pass 上传，避免 callback 在另一 program current 时失效。

GPU 对三盏灯逐片元执行 pow，代价高于硬 step/乘法。先用 `max(lambertTerm,0)` 保证定义域，再令 `spot=smoothstep(cosOuter,cosInner,cosTheta)`、`shaped=pow(spot,exponent)`。验收要求 cutoff 改变范围而 exponent 只改变内部集中度，两控件不再互相改职责。

## 6.9 混合方程

[源码：ch06_09_blending.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch06/ch06_09_blending.html)

本例 GUI 可改变 source factor、destination factor、equation 和 constant blend color。通式是：

```text
result = equation(sourceColor × sourceFactor,
                  destinationColor × destinationFactor)
```

source 是当前片元 shader 输出，destination 是 framebuffer 原值。`blendColor` 只有选择 CONSTANT_COLOR/ALPHA 因子时才参与。

常用组合：非预乘 alpha 用 SRC_ALPHA / ONE_MINUS_SRC_ALPHA；预乘 alpha（RGB 已乘 A）用 ONE / ONE_MINUS_SRC_ALPHA；加法粒子常用 SRC_ALPHA / ONE。预乘贴图若误用 SRC_ALPHA 会把边缘再乘一次，产生暗边。

`blendEquation(FUNC_ADD/SUBTRACT/REVERSE_SUBTRACT/MIN/MAX)` 与 factors 独立。若需要 RGB 与 alpha 不同规则，用 `blendFuncSeparate` 和 `blendEquationSeparate`。

源码同时启用 depth test、blend、cull。深度测试通过后才混合；若透明物体仍写深度，先画的透明表面会挡住后画表面。混合本身不会排序或自动关闭 depth write。

验收：选一个像素，手算红 `(1,0,0,.25)` 覆盖蓝的结果，与 readPixels 对照；交换绘制顺序验证不交换。切预乘方案时必须同时修改输入 RGB 和 blend factor。

## 6.10 面剔除

[源码：ch06_10_culling.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch06/ch06_10_culling.html)

三角形投影到窗口后的绕序决定正反面。默认 `frontFace(CCW)`，启用 CULL_FACE 后 `cullFace(BACK)` 丢背面；源码可分别以 FRONT/BACK 剔除来显示立方体内外表面。

剔除发生在光栅化前，可减少不可见三角形片元，但它不判断真正遮挡，只依据绕序。负尺度镜像会翻转 determinant 与绕序；应调整 frontFace、修模型索引或避免把镜像变换混入未处理的 draw。

源码画“后表面”时 `cullFace(FRONT)`，画“前表面”时 `cullFace(BACK)`，两遍顺序可用于透明封闭壳体的近似：先背后前。但它仍无法处理两个壳体相交，也不能替代一般的 back-to-front 排序。

LINES 不形成有正反面的填充三角形；wireframe 分支的行为不能用三角形剔除直觉解释。所谓 wireframe 若只是把同一 triangle index 以 LINES 成对读取，也未必得到完整不重复的三角边。

调试缺面依次检查：index winding、frontFace、cullFace、模型是否有负尺度、法线方向是否与拓扑一致。验收时给 front/back 不同纯色，旋转立方体并逐项切换，不要同时改变 blend 和 alpha。

### Draw 次序

源码在同一 VAO 上可先设 `cullFace(FRONT)` 画背面，再设 `cullFace(BACK)` 画正面；每遍都执行完整光栅化/深度/混合。若两个开关都关则无 triangle draw，若 CULL_FACE 被 disable，cullFace 参数即使变化也不生效。

front/back 在窗口空间、透视除法之后按绕序判断，不由 normal 决定；翻 normal 只改光照，翻 indices 才改面分类。现代 render state 把 frontFace/cullMode 作为 Material/Pipeline key，pass 结束恢复，避免后续模型突然消失。

## 6.11 透明初始版

[源码：ch06_11_transparency-initial.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch06/ch06_11_transparency-initial.html)

场景把 cone 平移到 Z=-5、wall 到 Z=+5，材质中带 alpha，但 configure 只启用 depth test，没有启用 blend。因此 framebuffer RGB 被后通过深度测试的源片元覆盖，透明值本身不会让后面物体透出。

这个对照例适合按管线诊断，而不是直接“加一行 blend”结束：

1. shader 是否真的输出 alpha，而不是最终强制 1；
2. BLEND 是否启用；
3. blendFunc 是否匹配预乘策略；
4. depth test 是否开；
5. depthMask 是否仍写深度；
6. 透明物体是否从远到近排序。

不透明物体先画、深度测试与写入开启。透明阶段通常保持 depth test，关闭 depth write `depthMask(false)`，按观察空间深度 back-to-front 画，结束恢复 `depthMask(true)` 和 blend 状态。状态不恢复会污染下一帧/下一个 pass。

验收：先不改代码，预测 cone/wall 哪个遮住哪个；然后只开 BLEND，再只关 depth write，再交换顺序，形成 2×2 对照，逐图解释差异。

## 6.12 透明完成版及其边界

[源码：ch06_12_transparency-final.html](https://github.com/PacktPublishing/Real-Time-3D-Graphics-with-WebGL-2/blob/master/ch06/ch06_12_transparency-final.html)

相较初始版，本例加入 `enable(BLEND)` 和 `blendFunc(SRC_ALPHA,ONE_MINUS_SRC_ALPHA)`，因而能看到标准非预乘透明。但“final”只表示完成本书这一小步，并非通用透明渲染器。

源码仍按 scene traverse 顺序绘制，未建立 opaque/transparent 队列；也未在透明 pass 关闭 depth write。若较近透明物体先写深度，之后较远透明物体会被 depth test 丢弃，根本没有机会参与混合。

基础工程结构：

```js
// opaque
gl.disable(gl.BLEND);
gl.depthMask(true);
drawOpaqueFrontToBack();

// transparent
gl.enable(gl.BLEND);
gl.blendFunc(gl.SRC_ALPHA, gl.ONE_MINUS_SRC_ALPHA);
gl.depthMask(false);
drawTransparentBackToFront();
gl.depthMask(true);
```

排序键可用对象包围球中心变到 eye space 后的 z，但它只能排序对象，不能解决三角形互穿、自相交或大透明面横跨深度范围。更精确需拆分/逐三角形排序，或采用 order-independent transparency（如 weighted blended OIT），各有成本与近似。

还要区分材质 opacity 与纹理 alpha；颜色纹理通常需 sRGB 解码后在线性空间照明/混合，再编码显示。WebGL 默认 framebuffer 的颜色行为需结合创建参数和扩展验证。

最终验收必须包含至少三层彩色透明面，旋转相机让深度顺序改变；每帧重排后颜色关系应随视角正确变化。再加入不透明物体，确认透明物体被其遮挡但不会错误遮掉彼此。
